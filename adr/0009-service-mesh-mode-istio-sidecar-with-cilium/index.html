ADR-0009: Service mesh mode — Istio sidecar with Cilium¶

  • Status: Accepted on 2026-10-23 by the Technical Design Authority and the Project Leader
  • Date: 2026-10-03
  • Deciders: Technical Design Authority (Kevin Kupilas), Project Leader (Robert Koning)
  • Proposer: the delivery team, from the WP05 mesh feasibility gate
  • Supersedes: ADR-0001 — Service mesh mode, Istio Ambient with Cilium. That record keeps its text and carries the superseded status; this one is the superseding record its fallback clause requires.
  • Requirement basis: SRS 2.3.3, SRS § 5.1.2, SRS Table 4; ZT-23, ZT-24, ZT-26, ZT-55, ZT-58, ZT-60, ZT-61
  • Evidence: docs/evidences/mesh-mode-upstream-state/, regenerated by scripts/mesh-mode/check-upstream-state.sh

Context¶

ADR-0001 baselined the service mesh on Istio ambient mode with Cilium as the CNI and made the baseline conditional on a feasibility gate in WP05: if the gate failed, the pre-approved fallback was Istio sidecar mode with Cilium held to L3/L4, "recorded as a superseding ADR". The decisive question of that gate is whether the mesh can obtain its workload identities from SPIRE under ambient mode.

The requirement is not open to interpretation. SRS § 5.1.2 states that the service mesh "MUST be configured to fetch the certificate on behalf of each pod (e.g., SPIRE-delegated identities API) and use it in mutual TLS". ZT-24 states that "the service mesh MUST use SPIRE deployment to provide service identities. Identity verification MUST be based on SPIRE as well". ZT-60 states that a workload without a SPIRE identity cannot connect to any service in the mesh. The mesh's own mTLS identity must therefore be SPIRE-issued: this is the strict reading, and it is fixed by the SRS text, not chosen here. Two weaker readings were considered and rejected. Coexistence, with SPIRE SVIDs for the application layer and istiod certificates for the mesh, fails ZT-24 and ZT-60 outright, because a pod with no SPIRE entry still joins the mesh. Hybrid, with istiod as an intermediate CA under the SPIRE root in the same trust domain, chains to SPIRE but leaves issuance and attestation with istiod, and "identity verification MUST be based on SPIRE" reads against it.

The gate is answered by the upstream itself. The facts below are dated and versioned, and the evidence record linked above regenerates them from the sources:

  • Istio 1.31.1 (released 2026-09-21) is the latest community release. Its migration guide from sidecar to ambient lists, under What is not supported: "SPIRE as the certificate provider. Ambient mode does not support SPIRE integration."
  • istio/istio#42339, "SPIRE integration with Ambient", has been open since December 2022 (last activity 2026-09-18).
  • The upstream direction is the SPIFFE Broker API: a SPIRE agent endpoint through which an infrastructure component such as ztunnel obtains SVIDs on behalf of the workloads it references. SPIRE 1.15.3 (released 2026-08-21) ships it under the agent's experimental configuration block.
  • In ztunnel, #2067 (merged 2026-09-22) is groundwork only — per-workload keys in the certificate cache; #1936, the Broker API client, is a draft marked do-not-merge; #1676, the Delegated Identity API client, is open with review pending. None of this is in a release.
  • The only working ambient + SPIRE path is a commercial distribution (Solo Enterprise for Istio, through the Delegated Identity API). It is not a community release and is not an option for this demonstrator.

Under ambient mode with community Istio, ztunnel takes its certificate from istiod regardless of any SPIRE registration, so ZT-24 and ZT-60 cannot be met. The gate fails on documentary evidence; the accepted risk and its mitigation are recorded under Consequences.

What the repository already has: the umbrella chart (deployment/helm/ztd) switches mode with one value, mesh.mode, which changes one namespace label, and its evidence on kind with Cilium 1.20.2 chained (cni.exclusive=false) proves the plane layout, the default deny, the idempotent install and the live switch between the modes. Nothing in the repository installs Istio or SPIRE yet; the identity and mesh work waits on one recorded mode.

Decision¶

The implementation baseline is Istio sidecar mode with Cilium as the CNI.

  1. Cilium stays configured with cni.exclusive=false so that the Istio CNI plugin chains behind it. The Istio CNI plugin is the recommended traffic-redirect path in sidecar mode too, so the chaining, and the check of it after every Cilium upgrade (WP12), are unchanged.
  2. Exactly one L7 enforcement owner is assigned per traffic path. Where the Envoy sidecar enforces L7 policy on a path, Cilium is held to L3/L4 on that path, and vice versa. The assignment is recorded per traffic path in the mesh configuration, as ADR-0001 already required and as SRS Table 4 demands ("L7 policies MUST NOT be enforced by both simultaneously").
  3. SPIRE-issued SVIDs are delivered to mesh workloads through the SPIFFE CSI driver (ZT-24) and consumed by the Envoy sidecar over the SPIRE agent's SDS endpoint. This is the documented community path for Istio with SPIRE: a workload without a SPIRE entry receives no certificate and cannot join the mesh (ZT-60).
  4. Sidecars are injected as native sidecar containers (ENABLE_NATIVE_SIDECARS, see the security note). The istiod value that turns this on belongs to the Istio installation and is set there.

The umbrella chart's default follows the decision: mesh.mode defaults to sidecar, the CI zone file and the example zone file set sidecar, and rendering with the default labels every plane namespace istio-injection=enabled. The IONOS cluster is out of scope for this record: it runs Calico, holds no demonstration workload and no mesh, and its zone file keeps mesh.mode: none.

Consequences¶

  • Positive: the mesh identity is SPIRE-issued, which is what ZT-24 and ZT-60 demand and what the fail-closed scenarios of ZT-26 and ZT-55 assert. The identity, registration, install-ordering and mesh-enrolment work proceeds on a mode the upstream supports.
  • Positive: the flip costs the chart one default and the zone files one value; the plane separation, the default deny and the allow matrix are mode-independent, and the umbrella evidence already proved the switch in both directions.
  • Negative: the verdict rests on documentary evidence, and the contract's Annex A rule 2 asks for executed positive and negative tests. Accepted: an executed negative (SPIRE under ambient on kind, showing the mesh ignores it) would prove what Istio states in writing. Mitigation: the evidence record is dated, versioned and regenerated by a script, is explicit about being documentary, and an executed probe on kind (community Istio in ambient over the chained Cilium, showing ztunnel's certificate source is istiod and that the ztunnel chart has no SPIRE option) is specified as a conditional task to add if the review of this record asks for it.
  • Negative: sidecar mode has the per-pod proxy footprint ambient was chosen to avoid. See the security note.
  • Negative: the SPIRE + sidecar + Cilium proof end to end — SPIRE server, agents, CSI driver and controller-manager; istiod with native sidecars; a workload registered by selector obtaining an SVID that the sidecar presents in mTLS; the default deny still enforced with Cilium chained — is its own change, proposed after this record, carrying the istiod values. This record unblocks it; it does not contain it.

Security note¶

  1. Surface. One Envoy proxy per pod instead of one ztunnel per node: more processes and more images to sign, verify and keep patched, and a proxy inside every workload's pod. Accepted because it buys per-pod identity and mTLS issued and attested by SPIRE, which is what ZT-24 and ZT-60 demand and what ambient could not deliver; for a Zero Trust demonstrator the identity is the point, and the per-pod proxy is a net gain.
  2. L7 ownership. Where the sidecar enforces L7 on a path, Cilium is held to L3/L4 on that path, and the assignment is recorded per path in the mesh configuration, so no path has two L7 enforcement owners. This is the rule SRS Table 4 states ("L7 policies MUST NOT be enforced by both simultaneously") and ADR-0001 point 2 already carried; without waypoint proxies the assignment is simpler, because the sidecar is the only Istio L7 point on a path.
  3. Injection. Sidecars are injected as native sidecar containers, generally available since Kubernetes 1.33, on every cluster. This fixes the proxy/application start order (the proxy is ready before the application container starts, so no connection leaves before mTLS can be enforced) and lets Jobs terminate when their main container ends. Each cluster's Kubernetes version is recorded against this requirement in its zone file (zone.kubernetesVersion): the known clusters run 1.35 (the IONOS cluster v1.35.6, the local kind cluster v1.35.8); the two OSC clusters record theirs at stand-up. A cluster below 1.33 cannot take this baseline as is.
  4. What is given up. ADR-0001 credited ambient mode with keeping the participant and protected-resource mocks replaceable without touching the mesh configuration (WP09 Definition of Done). In sidecar mode that property rests on namespace-level injection: a replacement that lands in a labelled plane namespace is injected without any mesh change. The umbrella chart already sets the label, so the practical cost is nil, but the dependency is written down here.

Ambient is parked, not abandoned¶

The client's preference for ambient mode (ZT-58 cites the ztunnel daemon as an example) is recorded. The ambient path stays available and unused: the chart's values schema keeps accepting ambient, the Cilium host-probe exception still renders in that mode, the umbrella verification proves the live switch to ambient and back on every run, and no zone file in the repository sets it. Returning is a zone value, not a chart change.

What would reopen this decision¶

Both of the following, in released versions:

  1. Istio. A community Istio release whose ztunnel obtains workload certificates from the SPIRE agent through the SPIFFE Broker API, documented as supported in ambient mode. As of Istio 1.31.1 (2026-09-21) the migration guide lists SPIRE as the certificate provider under What is not supported; the ztunnel client for the Broker API (istio/ztunnel#1936) is an unmerged draft.
  2. SPIRE. A SPIRE release in which the Broker API is a stable agent feature, outside the experimental configuration block. As of SPIRE 1.15.3 (2026-08-21) it is experimental.

One without the other does not reopen it: a stable SPIRE API with no community consumer, or an Istio client against an experimental API, leaves the demonstrator on a path the upstream does not support. A commercial distribution that bridges the gap (Solo Enterprise for Istio does, through the Delegated Identity API) does not count. The check is made at every Istio minor upgrade, alongside the CNI chaining check that WP12 already runs after every Cilium upgrade, by running scripts/mesh-mode/check-upstream-state.sh: it exits non-zero and names the premise when the unsupported statement is gone, a client pull request has merged, or the Broker API has left the experimental block.
